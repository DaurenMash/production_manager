# Схемы БД (DBML)

Здесь лежат описания схем баз данных по сервисам в формате [DBML](https://dbml.dbdiagram.io/docs/).

## Зачем

- Единый источник «как выглядят данные» — открывается в [dbdiagram.io](https://dbdiagram.io) или VS Code (расширение DBML).
- Быстрая навигация по проекту: не надо лезть в миграции Liquibase.
- Документ для обсуждения — проще показать схему, чем описывать словами.

## Правила

1. **Один файл на сервис:** `<service-name>.dbml` (например, `employee-service.dbml`).
2. **DBML обновляется в том же PR**, что меняет Liquibase-миграции.
3. **DBML — это намерение, а не отражение.** Здесь описывается то, что *должно быть* в схеме, а не то, что случайно получилось в живой БД.
4. **Не дублировать типы из Liquibase построчно** — только структура, ключи, связи, важные индексы.
5. **Мультитенантность.** Каждая бизнес-сущность принадлежит организации (`tenant_id`). Это правило обязательно к соблюдению во всех схемах.

## Автоматизация (позже)

Полностью автоматической синхронизации «БД → DBML» из коробки нет — DBML это формат *проектирования*, а не *отражения*.

Когда дойдём до CI, добавим:
- **`tbls`** (https://github.com/k1LoW/tbls) — генерирует markdown-доку по **живой** БД (PostgreSQL). Коммитим как `docs/db/<service>/README.md` (сгенерировано).
- Проверка в CI: если миграции изменились, а `schema.dbml` — нет, падаем.

Пока (до CI) — правило №2 работает на дисциплине: обновляем в том же PR.
