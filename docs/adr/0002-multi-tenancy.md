# ADR-0002. Мультитенантность: shared schema + tenant_id

Дата: 2026-10-01
Статус: Принято

## Контекст

ProdMan — SaaS-приложение. Клиенты (организации) регистрируются, получают личный кабинет и работают со своими данными: сотрудники, отделы, должности, станции, расписания, тесты. Данные одного клиента **не должны** быть видны другому.

Требуется выбрать модель изоляции данных.

## Альтернативы

### A. Separate database per tenant
Каждому клиенту — своя БД.
- **Плюсы:** максимальная изоляция, проще удалить клиента целиком.
- **Минусы:** тяжело масштабируется по числу клиентов (сотни БД), сложнее миграции (нужно применять в каждой БД), дорого по ресурсам на старте. Не подходит для нашего этапа.

### B. Separate schema per tenant (PostgreSQL schemas)
Одна БД, у каждого клиента — своя схема.
- **Плюсы:** хорошая изоляция, одна БД — проще бэкапы.
- **Минусы:** количество схем упирается в лимиты PostgreSQL при больших числах; миграции надо катить во все схемы; усложняет `database-per-service` (сервисов много).

### C. Shared schema + `tenant_id` (выбрано)
Одна БД, одна схема, у каждой бизнес-таблицы — колонка `tenant_id`.
- **Плюсы:** простота, единый набор миграций, легко добавить нового клиента (просто запись в `tenants`), хорошо для нескольких тысяч клиентов.
- **Минусы:** нужна дисциплина фильтрации по `tenant_id`; утечка = возможный доступ к чужим данным; индексы должны включать `tenant_id`.

## Решение

Принимаем **вариант C — shared schema + `tenant_id`**.

Правила:

1. У каждой бизнес-сущности есть колонка `tenant_id UUID NOT NULL`.
2. `tenant_id` ссылается на `Tenant` в `user-service` (межсервисная ссылка по идентификатору, не FK).
3. Запросы **всегда** фильтруются по `tenant_id`. Гарантия на уровне слоя репозиториев (Hibernate `@TenantId` или явные спецификации).
4. `tenant_id` **никогда** не приходит в теле запроса от клиента. Источник — JWT.
5. Gateway извлекает `tenantId` из JWT и прокидывает во внутренние сервисы через заголовок `X-Tenant-Id`.
6. Уникальные бизнес-ключи — составные: `(tenant_id, code)`.
7. Индексы на «горячих» полях — составные с `tenant_id` первым: `(tenant_id, status)`, `(tenant_id, employee_id)` и т.д.

## Последствия

**Плюсы:**
- Единый набор миграций Liquibase.
- Просто масштабируется по числу клиентов.
- Легко делать аналитику по платформе (агрегаты по всем тенантам).
- Не нужны отдельные схемы для каждого сервиса × тенант.

**Минусы / риски:**
- Ошибка фильтра = утечка данных между клиентами. Митигируем:
    - автотесты на изоляцию (для каждого сервиса);
    - код-ревью с чек-листом «есть ли `tenant_id` в запросе?»;
    - в IDE — правило checkstyle/ArchUnit, запрещающее репозиторные методы без `tenantId`.
- Возможен «шумный сосед» (один тенант грузит БД). Митигируем индексами и (позже) ограничениями по rate-limit.

## Что это меняет в коде

- В JWT — `tenantId`.
- В `user-service` — сущность `Tenant`.
- В каждом бизнес-сервисе — фильтр `TenantFilter`, читающий `X-Tenant-Id`, и `TenantContext` (ThreadLocal).
- В репозиториях — методы вида `findAllByTenantId(...)` или общий базовый репозиторий с обязательным `tenantId`.
