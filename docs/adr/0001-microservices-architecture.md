# ADR-0001. Микросервисная архитектура

Дата: 2026-09-30
Статус: Принято

## Контекст

ProdMan — система для менеджера производства: расстановка сотрудников по рабочим станциям и расчёт часов (включая ночные). Домен делится на явные подобласти:

- пользователи и доступ (аутентификация, роли, аудит);
- сотрудники, отделы, должности;
- рабочие станции;
- расписания и смены;
- тесты квалификации;
- клиенты платформы (тенанты) и их жизненный цикл (триалы, планы, блокировки);
- уведомления (позже) и платежи (позже).

Части системы развиваются с разной скоростью и имеют разную нагрузку (расчёт часов — тяжёлый и периодический, аутентификация — частая и легковесная).

## Решение

Разбить backend на отдельные сервисы:

- `user-service` — организации, пользователи, роли, JWT, аудит, управление тенантами (для `PLATFORM_ADMIN`).
- `employee-service` — сотрудники, отделы, должности, квалификации, tenant_settings.
- `workstation` — рабочие станции + `workstation_qualifications`.
- `work-calendar` — расписания, смены, слоты, отчёты, ref-кэш квалификаций.
- `test-service` — тесты квалификации.
- `prodman-api-gateway` — единая точка входа, JWT-фильтр, прокидывание `X-Tenant-Id`.
- Позже: `notification-service` (SMTP + шаблоны + outbox), `payment-service` (подписки, `subscription_ends_at`).

Каждый сервис — со своей БД (database-per-service). Общение — через REST, синхронно.

## Альтернативы

1. **Модульный монолит.** Проще запускать, дешевле по инфраструктуре, легко рефакторить границы. Отклонено: домен уже разделён на уровне команд и предметных областей, планируется независимый деплой.
2. **Монолит + выделенный сервис для тяжёлых расчётов.** Частично разумно, но требует тех же механизмов маршрутизации/аутентификации.
3. **SOA через брокер (Kafka/RabbitMQ).** Избыточно на текущем этапе; Redis используется для кэша, но не как шина.

## Последствия

**Плюсы:**
- Независимый деплой и масштабирование (например, `work-calendar` — отдельно).
- Чёткие границы домена, проще reasoning.
- Разные БД — нет связности на уровне схемы.
- `PLATFORM_ADMIN` и аудит пользователей живут в `user-service`, не размазываются по сервисам.

**Минусы:**
- Сложнее локальная разработка (нужно поднимать несколько сервисов).
- Распределённые транзакции отсутствуют как класс — нужны саги/согласованность на уровне домена (пока отложено).
- Дублирование инфраструктурного кода (security, logging, `TenantFilter`, `TenantContext`).
- Повышенные требования к контрактам API.
- Имперсонация (`PLATFORM_ADMIN` → тенант) требует аккуратной работы с JWT и аудитом.

## Следствия для разработки

- API-контракты фиксировать в `docs/api/`.
- Межсервисное общение — только через Gateway для клиента и напрямую по внутренней сети для сервисов.
- `X-Tenant-Id` — единственный способ передать `tenantId` от Gateway к сервису; в JWT — источник истины.
- `PLATFORM_ADMIN` — отдельная роль, не входящая в иерархию тенанта; доступ к платформенным эндпоинтам только через `hasRole('PLATFORM_ADMIN')`.
- Любые новые сервисы — только через ADR.
