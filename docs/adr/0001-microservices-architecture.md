# ADR-0001. Микросервисная архитектура

Дата: 2026-09-30
Статус: Принято

## Контекст

ProdMan — система для менеджера производства: расстановка сотрудников по рабочим станциям и расчёт часов (включая ночные). Домен делится на явные подобласти:

- пользователи и доступ (аутентификация, роли);
- сотрудники, отделы, должности;
- рабочие станции;
- расписания и смены;
- тесты квалификации.

Части системы развиваются с разной скоростью и имеют разную нагрузку (расчёт часов — тяжёлый и периодический, аутентификация — частая и легковесная).

## Решение

Разбить backend на отдельные сервисы:

- `user-service`
- `employee-service`
- `workstation`
- `work-calendar`
- `test-service`
- `prodman-api-gateway` (единая точка входа)

Каждый сервис — со своей БД (database-per-service). Общение — через REST, синхронно.

## Альтернативы

1. **Модульный монолит.** Проще запускать, дешевле по инфраструктуре, легко рефакторить границы. Отклонено: домен уже разделён на уровне команд и предметных областей, планируется независимый деплой.
2. **Монолит + выделенный сервис для тяжёлых расчётов.** Частично разумно, но требует тех же механизмов маршрутизации/аутентификации.
3. **SOA через брокер (Kafka/RabbitMQ).** Избыточно на текущем этапе.

## Последствия

**Плюсы:**
- Независимый деплой и масштабирование (например, `work-calendar` — отдельно).
- Чёткие границы домена, проще reasoning.
- Разные БД — нет связности на уровне схемы.

**Минусы:**
- Сложнее локальная разработка (нужно поднимать несколько сервисов).
- Распределённые транзакции отсутствуют как класс — нужны саги/согласованность 
- на уровне домена (пока отложено).
- Дублирование инфраструктурного кода (security, logging).
- Повышенные требования к контрактам API.

## Следствия для разработки

- API-контракты фиксировать в `docs/api/`.
- Межсервисное общение — только через Gateway для клиента и напрямую по внутренней сети для сервисов.
- Любые новые сервисы — только через ADR.
